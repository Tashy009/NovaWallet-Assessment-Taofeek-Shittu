# AI Usage

## 1. Tools used

| Tool | Used for |
|---|---|
| **Claude Code** (Anthropic), in VS Code | The only AI tool used. Architecture proposal, code generation, SQL, tests, running builds/tests/Docker, debugging, and drafting these docs. It also helped set up the local environment (PostgreSQL login, WSL 2 and Docker Desktop). |
| | **In the final review phase** I also used it as a reviewer and tutor: explaining code line by line so I could defend it live, answering security questions (404 vs 403, SQL injection, scopes), finding gaps against a test checklist, and rewriting the README. |

**How I worked with it.** I wrote the requirements and constraints, made the architectural calls, and gated every phase: nothing moved on until the phase built and its tests passed. Most of the code was generated by the AI. My job was to direct it, challenge its design, and **verify every claim with tests against a real database** rather than trusting its reasoning. I also asked it explicitly not to invent AI mistakes for this document; everything below happened and is reproducible from the repo.

## 2. Concrete prompts and what came back

### Prompt 1: architecture before any code
> "The transfer implementation must guarantee: No negative balance · No double spending … Do NOT implement: `read balance / if balance >= amount / subtract amount / save balance` unless you can prove it is concurrency-safe. Prefer database-enforced concurrency guarantees such as an atomic conditional UPDATE and/or appropriate row locking … When you identify a potential race condition, demonstrate exactly how it can happen before proposing the fix. … Before writing implementation code: propose the final architecture, the database schema, the exact concurrency strategy … Then STOP."

**What came back:**
- A layered design, a schema with constraints, and a transfer flow.
- **Locking:** lock both wallet rows with `ORDER BY id FOR UPDATE`, then a guarded debit, with a `CHECK (balance >= 0)` backstop.
- **Idempotency:** claim the key with `INSERT … ON CONFLICT DO NOTHING` *inside* the money transaction.
- **Daily limit:** a per-day totals table.
- **Race interleavings:** it showed the double-spend, A↔B deadlock and limit-overshoot interleavings step by step.

I approved it with changes (§4).

### Prompt 2: the transfer phase, with a stop condition
> "For transfers, implement and test: PostgreSQL wallet row locking using deterministic database-side ordering · atomic conditional debit · atomic destination credit · daily-limit enforcement · idempotency claim and replay … When implementing concurrency-sensitive code, explain the invariant being protected and show the SQL responsible for protecting it. IMPORTANT: If you encounter a design choice that could affect money correctness, STOP and explain the issue before implementing a potentially unsafe solution."

**What came back:**
- **Implementation:** the transfer unit of work, a retry policy for `40P01`/`40001`, and a test suite including 100-way concurrency, a 100-way same-key test and opposing A↔B transfers.
- **Design flags it raised before implementing:**
  - Rejections (e.g. insufficient funds) should be stored against the idempotency key, so a replay returns the same answer.
  - Replays should return the *original* status code rather than `200`.
  - The destination row must be locked up front, not just the source, or opposing transfers deadlock.

### Prompt 3: pushing back on structure
> "use the clean architecture not the minimalist endpoint"
>
> "why is interface not use, i want it follow SOLID principle"

**What came back:** first, the Minimal API endpoints were moved to MVC controllers. Then a SOLID refactor:
- Controllers depend on `IWalletService`, `ITransferService` and the other service interfaces.
- `TransferService` was split into a validator, a serializer and a retry policy.
- The large unit of work was segregated into four narrow interfaces over one shared transaction.
- New unit tests ran the transfer logic against fakes.

**Where it pushed back, and I agreed:** validators and hashing stayed static pure functions instead of interfaces, since an interface there adds ceremony with no testability gain.

### Prompt 4: a security question that exposed a logging gap
> "is this the best way to treat when another customer trying to view another customer balance"
>
> "is there log on this project" · "yes"

*(Quoted as typed, with spelling corrected.)*

**What came back:**
- **The answer:** keep returning `404` instead of `403`, so wallet IDs cannot be probed (OWASP API1, broken object-level authorization). It also suggested checking ownership in the SQL, and logging the attempt, because a probe and a typo currently look identical.
- **The follow-up check:** Serilog was set up in the API and infrastructure layers, but the **Application layer had no logging at all**, so cross-customer attempts and business rejections left no trace beyond a status code.
- **The change, after I said yes:** see Case 6.

### Prompt 5: closing gaps against a test checklist
> "[a checklist of ~24 areas: wallet, credit, transfer, concurrency, idempotency, daily limit, ledger, audit, security, failure, logging, input attacks, DB invariants, deployment] … make sure all these tests are covered and add a simple comment to each test case"

**What came back:**
- **A gap analysis first.** It read all 145 existing tests and mapped them to the checklist before writing anything. Most items were already covered; about 25 were not.
- **65 new test cases (145 → 210)**, including four new test classes:
  - `FailureAtomicityTests`: a wrapped unit of work throws **after the debit**, **before the audit write** or **at commit**. The tests assert nothing persists (balances, transaction, audit, daily total, idempotency key, outbox event), the `500` leaks nothing, and the same key then succeeds exactly once.
  - `AuthenticationTests`: expired, wrongly signed, wrong-issuer, wrong-audience, unsigned and `sub`-less tokens, and a weak signing key that must stop startup.
  - `InputSecurityTests`: SQL injection in narration, JWT `sub`, route and reference; `long` overflow and `1e30`; malformed JSON; no internals in error bodies.
  - `LoggingSecurityTests`: captures every Serilog event and asserts no bearer token ever appears.
- **A one-line comment on every test** naming the checklist item it covers.
- **Places where it disagreed with the checklist** instead of writing a test to match it (see §4).

## 3. Where the AI was wrong, unsafe or naive, and how it was caught

### Case 1: a daily-limit ordering flaw that would miscount money (financial logic)
**What the AI proposed.** In its first draft of the transfer flow, the conditional daily-limit upsert ran *before* the balance check and debit, and business rejections were committed so they could be replayed by idempotency key.

**Why that is wrong.**
- **Limit first:** a transfer that passed the limit step but then failed on insufficient funds would commit the `daily_outbound_totals` increment along with the rejection record. The customer's ₦500k allowance would shrink for money that never left the wallet.
- **Debit first:** reversing the order would debit first, then hit the limit, and a committed rejection would persist the debit.

Either way, one transaction would mix a rejection with a partial write.

**How it was caught.** It surfaced while the AI was checking its own draft for which writes could be committed alongside a rejection. It flagged the problem in the architecture write-up before any code existed. So this was caught by review of the design, not after an incident. I made it a design rule.

**Fix.** Every check (ownership, status, funds, daily limit) runs **under the row lock and before any write**. A rejection commits only the idempotency outcome. The guarded SQL stays as a second line of defence, but it can only fire as an invariant violation that rolls back everything.

**How it was validated.**
- `TransferServiceTests.Insufficient_funds_stores_the_rejection_and_commits_without_touching_balances` (fakes) asserts a rejection commits with **no balance mutation and no journal writes**.
- `DailyLimitTests.Transfer_that_would_cross_the_limit_is_rejected_whole` and `Concurrent_transfers_never_exceed_the_daily_limit` assert the stored daily total is **exactly** ₦500,000 after 30 concurrent attempts.

### Case 2: a controller attribute silently broke RFC 7807 error responses
**What the AI produced.** When converting to controllers, it put `[Produces("application/json")]` on the shared `ApiControllerBase`.

**Why that is wrong.** The attribute overrides the `application/problem+json` content type on every error, so the API no longer honoured the structured-error contract the brief requires. Clients keying on the media type would treat errors as normal payloads.

**How it was caught.** Two existing integration tests failed straight away (`Expected: "application/problem+json" / Actual: "application/json"`).

**Fix.** Removed the attribute; all tests pass.

### Case 3: logs reported `500` when the client actually got `503`
**What the AI produced.** The initial pipeline registered `UseExceptionHandler()` *before* `UseSerilogRequestLogging()`, so the request logger sat **inside** the exception handler.

**Why that matters for a ledger.** During the deadlock experiment below, the logs showed `responded 500` and an `UnhandledException` error for every request. The test assertions, though, showed the client received `503 Service Unavailable` with `Retry-After`: "rolled back, safe to retry". An on-call engineer reading those logs would conclude money operations were crashing, when they were being rolled back and safely retried. Misleading operational data in a payments system leads to wrong incident decisions.

**How it was caught.** Comparing the log output with the test's actual assertion output during the deadlock experiment in §5.

**Fix (Phase 6).**
- Request logging now wraps the exception handler.
- .NET 8's duplicate `ExceptionHandlerMiddleware` log is silenced in config.
- `LedgerExceptionHandler` logs at the right level: Warning for 503, Error for 500.

### Case 4: a verification step that gave a false result
**What happened.** To prove the schema tests work, the AI removed a CHECK constraint and a trigger from the migration, confirmed the expected 3 failures, then restored the file with `Copy-Item` from a backup. The tests **still failed**.

**Cause.** `Copy-Item` preserved the backup's *older* timestamp. MSBuild saw the DLL as newer than the SQL file, skipped the rebuild, and kept running the **tampered embedded migration**.

**How it was caught.** It didn't accept "flaky" as the explanation. It checked that the file content was actually restored, then compared file and DLL timestamps.

**Lesson applied.** After every later experiment, the restore was confirmed by grepping the file and re-running the full suite three times.

### Case 5: an unchecked token claim reachable as a `500`
**What the AI produced.** Every free-text input was length-validated against its database column (idempotency key, NIP reference, narration, correlation ID), **except the JWT `sub`**, which becomes `customer_id varchar(128)`.

**Why that matters.** A validly signed token from a real identity provider with a longer subject would reach the `INSERT` and fail with `value too long`, returning `500`. No money is at risk (the statement fails and nothing is written), but it is an unhandled input path and noisy error alerting on an auth edge case.

**How it was caught.** During the final review phase, the AI traced every externally supplied value to the column it lands in. A test issuing a signed token with a 129-character subject reproduced it: `Expected: Forbidden / Actual: InternalServerError`.

**Fix.** The customer authorization policy now requires a non-blank `sub` of at most 128 characters, so such a token gets `403`. The test passes, along with the full suite.

### Case 6: security-relevant events were invisible in the logs
**What the AI produced.** The ownership check in its services (`wallet is null || wallet.CustomerId != caller.CustomerId` → `404`) was correct, but the Application project did not even reference a logging abstraction. The only trace of a cross-customer request was `GET /wallets/{id}/balance responded 404`, exactly the same as a mistyped wallet ID. Business rejections (`insufficient_funds`, `idempotency_key_reused`, `external_reference_conflict`) were also logged only as a status code.

**Why that matters for a ledger.** Hiding a wallet's existence from the *client* is right, but hiding it from the *security team* is not. Someone enumerating wallet IDs, or a compromised account probing other customers, would be undetectable. Support staff also could not tell from the logs why a transfer failed.

**How it was caught.** By asking a design question (Prompt 4) and then checking the codebase rather than assuming logging existed.

**Fix.**
- Added `Microsoft.Extensions.Logging.Abstractions` to the Application layer, so Serilog stays in the API layer.
- `WalletService`, `StatementService` and `TransferService` log a **warning** only when the wallet exists but belongs to someone else, with the caller and wallet ID. A genuinely unknown ID is not flagged, and the client still gets the same `404`.
- A request-log enricher adds the business `ErrorCode` to every failed request's log line.

**How it was validated.** `LoggingSecurityTests` captures the real log events for a cross-customer read and asserts the warning (caller and wallet), `ErrorCode: wallet_not_found` and the correlation ID are present, and that no bearer token appears anywhere.

### Case 7: an AI-written test failed for the wrong reason
**What happened.** The first run of that logging test failed with `KeyNotFoundException: 'ErrorCode'`. The easy reactions would have been to change the enricher or loosen the assertion.

**Cause.** The test looked for "the log event whose `RequestPath` is this URL", expecting the request-completion line. But the new ownership warning is written inside the request's logging scope, so it **also** carries `RequestPath`. The test picked up the warning, which correctly has no `ErrorCode`.

**How it was caught.** It checked which event had matched before touching production code, and confirmed the production behaviour was correct.

**Fix.** The test now matches only the completion event (which has `StatusCode` and `Elapsed`). It passed, and the full suite was run twice more: 210/210 both times.

**Lesson.** A red test is a question, not an instruction. Changing the code or the assertion to make it green would have hidden either a real bug or a bad test.

## 4. Where I overrode or redirected the AI

| Decision | What happened |
|---|---|
| **Controllers over Minimal APIs** | The AI chose Minimal APIs for less ceremony; I asked for controllers instead. The existing tests caught the one regression the switch introduced (Case 2). |
| **SOLID / interfaces** | The AI's first version used concrete services. I required interfaces and segregation; the resulting fakes made it possible to unit-test rollback and retry paths without a database. |
| **Minimal code comments** | I asked for single-line comments only where needed. Explanations live in the README. |
| **Phase gating** | I required each phase to build and pass tests before moving on, and asked for proof that the concurrency tests can actually fail (§5). |
| **JWT earlier than planned** | The AI proposed moving auth forward because every endpoint needs the caller's identity, and deferring it would mean rewriting endpoints and tests. I accepted. |
| **Credit idempotency** | The AI proposed using the unique NIP `externalReference` instead of an `Idempotency-Key` header for credits, since a database-unique natural key is stronger. I accepted and documented it. |
| **A checklist scenario that could not detect a bug** | My checklist said: start at ₦100, credit ₦100 and transfer ₦100 at the same time, and expect ₦0 or ₦100. The AI pointed out that **every** ordering ends at ₦100, so the test would pass even if the code were wrong. It used 5,000 kobo with 10,000 in each direction instead, where the two valid outcomes (5,000 or 15,000) are distinguishable. |
| **Checklist vs. actual design** | My checklist expected `idempotency_key_reused` when a credit's key is reused. Credits are idempotent on the NIP reference, so the real response is `409 external_reference_conflict`. The AI tested the actual design and flagged the difference instead of changing working code to fit the list. |
| **Frozen wallets without a freeze API** | The checklist wanted frozen-wallet tests, but freezing is out of scope. Tests set `status = 'FROZEN'` directly in the database, and the README says so. |
| **Did not disturb a running environment** | The deployment check found my Docker stack already running on an older image. Rather than replace it, the AI built the new image to prove the Dockerfile still works and smoke-tested the running stack (health `200`, credit `201`, transfer `201`, correct balances), then told me to redeploy. |
| **Correctness over scale** | In the README I stated explicitly that database roles, key retention, distributed rate limiting, tracing and similar items are deliberately not built, because the brief values prioritisation and this version focuses on correctness. |

## 5. Validation experiments: proving the tests catch real money bugs

Passing concurrency tests only mean something if they **fail** against broken code. For each experiment I had the AI inject the classic naive implementation, run the suite, record the actual result, and restore.

| Injected naive implementation | Actual result |
|---|---|
| **Credit as read-then-write** (`SELECT balance` → compute → `UPDATE SET balance = @new`) | 50 concurrent 1,000-kobo credits **all returned `201 Created`**, but the final balance was **1,000 instead of 50,000**: 49 credits silently lost. Caught by `Concurrent_distinct_credits_are_all_applied_with_no_lost_updates`. The duplicate-reference test still **passed** (the unique index covered it), so one test alone would not have caught this. |
| **Lock wallets in request order** (source, then destination) | PostgreSQL raised `40P01 deadlock detected`; retries were exhausted and **93 of 100** opposing A↔B transfers failed with `503`, taking 33s. With `ORDER BY id FOR UPDATE`, all 100 succeed. |
| **Remove `FOR UPDATE`** entirely | No overspend happened, because the guarded `WHERE balance_kobo >= @amt` and the CHECK held. But **49 of the 90 expected `422 insufficient_funds` became `500` invariant violations**, and 4 daily-limit requests passed a stale check before the guarded upsert stopped them. The row lock provides correct behaviour; the conditional SQL is the safety net. |
| **Drop `CHECK (balance_kobo >= 0)` and the audit append-only trigger** | Exactly the 3 corresponding schema tests failed. |
| **Remove `FOR UPDATE SKIP LOCKED`** from the outbox relay's batch claim | 4 relays draining 40 pending events in parallel published **160 times**: every `TransferCompleted` delivered 4 times. Caught by `Concurrent_relays_never_publish_the_same_event_twice`. |

All mutations were reverted, and the full suite (145 tests at the time) passed.

**Later additions.** The final review phase grew the suite to **210 tests, all passing** (53 unit, 157 integration; last run 17 September 2026). The new failure-injection tests (`FailureAtomicityTests`) take the same approach as the experiments above: they deliberately break the transaction at a chosen point instead of only testing the happy path. The mutation experiments in this table were run on the 145-test suite and have not been repeated on the larger one.

## 6. Takeaways

- **Verify, don't trust.** The AI produced correct locking SQL, but the evidence that it was correct came from mutation tests against real PostgreSQL, not from the explanation. An integration test against an in-memory fake would have passed every naive version above.
- **Constraints steer the AI.** Stating "no read-modify-write", "database is the final authority" and "stop before anything unsafe" in the first prompt shaped the whole design. The AI raised money-affecting choices instead of quietly picking one.
- **Its mistakes were quiet ones.** Wrong content types, misleading logs, an ordering flaw that would miscount a limit, and security events with no log trail. None of them crash; all of them would reach production without tests that check exact status codes, media types, stored totals and log contents.
- **Questions find what generation misses.** The logging gap and the Unicode narration gap were not found by asking the AI to write code. They came from asking it to explain and justify code that already existed.
- **Tests can be wrong too.** Both a checklist scenario and an AI-written test would have given false confidence or pointed at the wrong code. Each red test got a diagnosis before any change.
